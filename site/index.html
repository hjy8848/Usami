Usami Benchmark × VAST-CoEvo · 环境、挑战与递归学习

在业务交互中发现问题，积累解决问题的方法

业务 Agent 的能力体现在行动中：它是否查清权限，是否理解资源依赖，是否在条件变化后仍能做出正确决策？一次任务的最终成功与失败，还需要结合工具调用和状态变化理解。

Usami Benchmark 将这些决策放进可组合的业务世界。身份、工具与业务规则固定，Agent 自主选择查询和操作；独立裁判根据实际状态变化判定结果。任务可以有多条合法路径，开放探索也有明确的验证依据。

VAST-CoEvo 在此基础上组织递归学习：Customer 分析 Service 的执行轨迹，从已暴露的错误与成功过程中的薄弱环节生成挑战；双方将交互经验提炼为 Skill，带入下一轮。环境与进化方法分别构成两项贡献，并通过同一套执行证据连接。

01 Usami Benchmark

一个业务世界，多种决策边界

一个世界里有具体的用户、项目和资源，以及它们的权限、状态与依赖。Service 通过查询工具了解情况，再用业务工具采取行动；World Engine 执行操作并更新状态。因此，前一步做了什么，会改变后一步能不能做。固定任务还会指定业务目标；开放探索则由 Customer 自己选择测试请求。

复杂度来自规则之间的耦合：付款成功不等于项目恢复，组织负责人不等于拥有计算操作权限，资源能启动也不等于能安全停止或删除。下面先看完整的 CloudOps 关系，再进入一个局部操作。

自由度在请求、路径与交互中

Customer Discovery 不指定一条任务脚本。Customer 可以选择可见的项目与资源，决定先查什么、提出什么请求、如何组合多轮交互，以及何时追问、换方向或结束。Service 同样自主决定查询和操作顺序。双方的选择都会影响后续交互，但不能改写身份、规则或裁判答案。

Customer / 测试选择

决定测试什么

正常业务、禁止操作、状态变化后的再次请求，以及多个条件交织的边界。

Service / 执行选择

决定怎样处理

查询事实、选择合法路径、解释拒绝，或为必要的额外操作请求授权。

World / 固定边界

行动改变状态

工具操作推进业务，独立规则判断对错；明确请求本身不会赋予业务权限。

可组合、可执行、可独立核验

Usami 将任务放在持续变化的业务状态中：目标允许多条合法路径，开放挑战仍有固定的验证依据。执行轨迹记录 Agent 真正做了什么，Reference 与 Oracle 独立判断是否合法，Replay 复现事件。这些机制共同连接任务评测、自由探索与后续学习。

四个领域，各自保留完整规则

同一套交互与证据接口连接不同业务结构。各领域有独立状态机与不变量，不能用一组通用条件替代。

多条路径，相同的业务目标

在正常初态下，db → cache → app 和 cache → db → app 都能达成目标。评分不要求匹配其中一条序列，而是检查目标、允许变化的范围和安全条件。增加无关写操作，即使最后启动了应用，也可能违反任务约束。

Goal-based Task Generator 的作用是从真实状态与 Reference Rules 派生可达目标，并验证操作间是否存在因果依赖。它按结构类别采样，而不是把公司名称和资源 ID 的变化当作任务多样性。图 1 展示其中的并行依赖结构：上游顺序可交换，前置条件必须满足。

将固定任务与开放探索分开测量

Service Task 测量给定目标能否被安全完成；Customer Discovery 提供初始业务世界，由 Customer 自主决定测试请求。一个应当被拒绝的请求也可以是有效测试，Service 正确拒绝与实际执行违规需要分别记录。

Track固定什么观察什么
Service Task世界、身份、目标、操作范围、工具与预算安全目标达成、终态约束、正确拒绝与执行成本

二者通过版本化 Manifest 固定实例、初态 Hash、模型配置、源码与分区。顾客身份和精确写授权先于 Service 工具调用建立，不能从工具参数反推授权。训练、开发与独立测试使用明确分区，分别保存实例与证据。

执行与判定分离

Reference Rules 给出操作的预期结果；World Engine 产生实际状态变化；Oracle 核对两者与授权。研究用 Sandbox 保留错误操作实际执行的可观察性，使 Service 的决策能力与 Engine 的拦截能力可以分别分析。离线 Replay 则复现已记录的事件，核验这些判断。

02 VAST-CoEvo

先观察执行，再提出挑战

挑战以 Service 的执行轨迹为依据。对于失败任务，Customer 分析错误发生的条件，扩大或变化同类测试；对于成功任务，Customer 检查中间的遗漏、补救与决策过程，提出假设，检验这次成功是否依赖特定条件。

Customer 将轨迹线索转化为对象明确、条件可判定的业务请求，Service 在固定身份、权限与预算下应对，再由 Oracle 核验结果。下面沿用 app、db 和 cache，展示成功与失败两种起点如何导向针对性挑战。

把一次交互，变成下一轮可用的方法

轨迹记录发生过什么，Skill 则保存以后怎样做。Customer 积累识别薄弱环节、组合挑战和继续追问的方法；Service 积累查询事实、检查前置条件、执行与验证的方法。它们应概括可迁移的经验，而不是记住某个资源 ID 或单道题的答案。

双方使用声明式 Skill 保存可迁移的方法，基础模型权重保持固定。每份 Skill 有明确角色、作用域与版本，修改内容可以检查，历史版本可以独立加载。上一轮形成的方法参与下一轮出题与决策，新交互再用于修订方法。

每一代先交互，再学习：当前 Customer 与 Service 产生探索轨迹，Oracle 验证并保存证据，双方依次 Reflection、提出 SkillPatch，并按各自的选择规则保存版本。下一代加载选中的 Skill，继续产生挑战和处理业务。下面展开这一更新过程。

两种角色，学习目标不同

在这个依赖案例中，Customer 可以进一步比较并行与链式依赖，检验 Service 是否只检查了部分前置条件。Service 可以提炼的原则是：启动前确认依赖状态；需要额外写操作时先确认授权，不能为完成目标自行扩大操作范围。

这类经验应描述可复用的策略，而不是记住一个资源 ID。Reflection 产生的 SkillPatch 仍需要满足 Schema、父版本、作用域、工具与资源标识限制，内容完整性由不可变 Snapshot 校验。

按角色选择版本，保留完整证据

Customer 采用 Static-Only Selection：静态检查通过即可更新，质量、发现能力和成本诊断不决定接受或回滚。Service 保留静态与动态 Gate，检查已知错误、合法业务完成、正确拒绝、违规和授权异常；候选被拒绝或返回 NOOP 时保留旧版。

每次 Reflection 至多生成一个提案，保留提案、选择结果与来源证据。下一代继承实际选中的 Skill；业务 Episode 从冻结初态开始，策略经验跨代积累，世界状态按实验实例独立管理。

让发现、修复与泛化分别可测

训练交互负责产生学习证据，开发验收负责选择 Service 候选，独立测试负责测量跨场景表现。训练结束后加载冻结版本，分别比较 Service 的改进与 Customer 对学习过程的贡献。

Service 动态 Gate 验收候选。Customer 诊断可选，且没有版本选择权。

独立测试

冻结版本再比较

固定 Customer、世界与预算比较 S₀ / Sₙ，另以交叉组合研究 Customer 的影响。结果不回流训练。

Service 评价同时统计合法任务完成、正确拒绝、真实违规与授权异常。Customer 评价区分有效请求、独立错误根因、重复探针与探索覆盖；双方分别记录模型调用、Token 和工具成本。比较版本时，初态、身份、模型、工具、预算与评分规则保持一致。

固定 Customer 的训练组与进化 Customer 的训练组采用相同条件，用于分离测试策略迭代的贡献。独立 Held-out 采用新世界与固定任务，测试结果不回流训练；交叉组合只加载已有 Snapshot，分别观察不同 Customer 与 Service 版本的作用。
