# 后续迭代：P1 → P2

当前协议、Goal Task 和组合留出作为基线。本轮已实现这些基础；以下业务扩展
尚未实现，不能将设计中的新状态描述为当前能力。

## P1：成员生命周期连接席位与套餐

先引入邀请/待加入、激活、停用/移除的显式状态转换，以及 Owner 不可删除、
唯一成员关系、跨组织邀请隔离与 active_count 容量限制。由独立 Reference
定义每个前置条件、原子变化和拒绝结果，再在 Engine/Sandbox 中实现对应操作；
不能为了容纳邀请默认放松席位不变量。

保持 Customer 身份固定，首先生成以下正常目标及真实依赖：

- Owner 扩席 → 新成员激活；省略扩席必须让激活不可行。
- Owner 停用/移除成员 → 降席位 → 降套餐；省略成员迁移或降席应使目标不可达。
- 新成员待加入 → 有权限的确认激活；区分流程信息依赖和实际状态依赖。

不把“修改成员角色”冒充成员数量变化；当前 role 写操作不会改变 active_count。
也不让 Service 换 actor 来模拟多人交互。多参与者流程如需实现，由 Harness
分别认证多个会话，并单独定义新的 Track/实例语义。

Goal Schema 下一版本需支持 Membership 与 Subscription 的联合终态、允许变化
字段清单与守恒/隔离 frame；搜寻至少两条合法解决路径并对每条关键边做真实
移除检验。按依赖图方向、角色、拒绝/恢复分支分配配额，冻结新 suite/goal/rules
版本及源码，原 v0.1 使用 Git release/source 继续复现。

P1 验收：合法与拒绝、临界容量、Owner 防护、重复邀请/激活、独立身份与授权、
多路径目标、真实因果边、Engine/Oracle/Replay 一致，以及 Train/Test 结构组合
留出而原子操作在训练可见。保留 v0.1 全测试和回归世界，新增版本不静默改变
旧数据或旧评分。

## P2：支付、账单周期与订阅激活/续期

P1 数据集稳定后再增加明确的 Invoice–Subscription–BillingCycle 关联与支付/
激活/续期生命周期。用确定性虚构 payment fixture；不接真实资金系统。先定义
支付幂等键、已付/失败/未付分支、周期关联、跨组织资源隔离和支付后激活的
原子性，避免支付成功但激活失败时的含混中间态。

产生新的可验证目标：

- 支付未付账单 → 激活 expired 订阅 → 扩席/改变套餐。
- 为下一账期支付/确认 → 续期；区分已经支付的幂等重试与错误账期。
- 支付失败 → 合法恢复路径 → 激活；错误不得靠改变 Oracle 算作成功。

当前操作不能把 unpaid 变 paid、expired 变 active，也没有账单到订阅周期的
关系，因而这些目标不能通过现有工具简单拼接得到。时间推进如必须加入，
由版本化 Harness 控制冻结时点与显式推进事件，不能让工具偷偷使用墙钟。

P2 验收：独立参考状态迁移、关联不变量、幂等/重复支付、周期边界、失败恢复、
状态隔离、目标/因果证明与回放。新的组合必须由实际 Test Goal 使用，不能
只在世界中旁置某个状态合取。按 v0.1 两个 Track 分别报告正常任务完成和
成功业务违规，授权失败、拒绝尝试与 Unknown 继续分开。
