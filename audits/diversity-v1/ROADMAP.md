# Usami Benchmark Expansion Roadmap

本轮仅审计；以下方案尚未实现。当前数据依据见 [REPORT.md](REPORT.md) 和
[results.json](results.json)。方案先解决可比性与真实依赖，再扩展业务面；不以
新增 API 数量或随机调用链长度作为质量指标。

## 1. 冻结两条不同的评测轨道

### Service Task Benchmark

建立有版本号的 `suite_id` 和可重现 Manifest，冻结 Generator/Rules/Oracle/Task
版本及源码哈希、初始世界、Customer 身份、正常业务目标、可信授权边界、工具
集合和交互预算。任务以可程序化检查的终态与必要安全约束定义，例如“授权
将席位降至符合 Starter 容量，再降至 Starter 套餐，其他组织不变”。
目标应允许多条正确计划，避免参考脚本成为唯一评分答案；程序检查目标达成、
真实状态变更、拒绝正确性和 Oracle 违规，分别报告结果与执行成本。

Train/Validation/Test 不能只凭世界 hash 或 Seed 去重。冻结前执行本审计：

1. 按匿名关系模板、决策分支和状态依赖图分组，再分配任务族。
2. 保证基础操作与单规则在 Train 可见，把某些真实依赖的组合留给 Test；
   同时保留一组明确标识的同分布任务，分别报告泛化和常规可靠性。
3. 对所有 Split 发布或私下保存结构频率、重叠矩阵、任务族映射、抽样配额和
   独立拒绝原因覆盖；建立禁止意外结构泄漏的断言。
4. 公布 Train/Validation 与非盲 Demo 的版本化 Manifest；Test 由评测方独立
   保存并承诺其哈希。不能用本次公开 Demo 充当盲测数据。第三方同一版本比较
   必须引用同一评测 Manifest，升级规则或任务时递增版本。

现有 `train_single`/`test_composed` 的跨组织角色与订阅前态合取是真实世界级
留出，可保留为一个抽样条件。但任务必须实际引用并需要这组关系，不能仅让
世界“旁边恰好存在”该组合而继续执行单组织任务。本次签名重叠表说明为什么
现有实例级防重无法替代任务结构级设计。

### Open-Ended Customer Discovery Benchmark

冻结世界、独立 Customer 身份、目标 Service 模型/提示/运行版本、业务工具及
顺序语义、授权控制器、Oracle、总轮次/模型调用/工具预算和随机性配置；不冻结
Customer 的攻击对话脚本。保存每次 Customer/Service 消息、授权证据、实际操作、
状态变化与 Oracle 结果，并通过现有 Interaction Replay 检查重现性。

独立报告：被拒绝的非法尝试、实际成功造成的违规、合法业务完成、重复发现和
未知判定。违规发现按程序可验证的状态/规则证据归并，不能按文本不同计为新
漏洞；分开记录 Customer 模型 Seed 与 World Seed。固定世界的多次重复实验应
报告置信区间及预算消耗。开放发现轨道不要求训练/测试攻击话术结构互斥，也
不能直接用本次脚本候选频率推断开放式发现能力。

## 2. 先增强已有业务的因果任务生成

当前构造器主要是单操作和三种固定链族。可以先不增加业务操作而改进下一版
Task Generator（本轮没有修改）：

- 从合法世界和可达终态反向生成 Goal，携带可验证授权；用真实规则搜索可行
  计划，再去掉冗余操作。目标评分不固定调用顺序。
- 对“提升角色→订阅/账单操作”和“降席位→降套餐”验证逐步移除前置操作确实
  改变后续可行性，区分初始状态已满足条件的简单实例。按依赖图分支、长度、
  深度、失败后恢复路径和系统边界分配配额，避免随机拼接。
  当前 `multi_entity` 构造器在 Owner 和目标成员之间切换 actor，而 Service/
  Interaction 会话固定 Customer 身份；此类候选不能直接作为单会话 Service
  目标。需要多个由 Harness 独立认证的会话才能测试这种权限传递，不得让
  Service 用工具参数切换身份。固定身份轨道应优先选择席位—套餐链。
- 增加跨组织角色对比目标：同一用户在 A 有 billing_admin、在 B 仅为 member，
  按独立授权完成 A 可行目标并正确拒绝 B。同一任务必须使用两个组织，保持
  资源与身份隔离。当前规则可验证这种分支，但它未必形成跨组织状态因果边；
  不能将“两个组织都有调用”宣传成跨组织因果工作流。
- 多账单目标可测试部分合法、部分过期/已退款的组合及重复执行防护；当前
  账单彼此独立，只能称并列决策覆盖，不能假设存在额度/余额依赖。
- 补足已实现但候选未覆盖的只读查询、billing_admin/member 修改角色拒绝、
  inactive target、无效套餐/资源与临界退款时间。对正常目标、恶意尝试、
  损坏世界/协议的 Oracle 压力测试分别建轨，不通过非法世界制造“丰富业务”。
- 将签名完整规范、示例和去重频率随版本发布。允许重复实例估计稳定性，但
  用固定配额控制常见单步退款模板，不让它们淹没罕见依赖链。

## 3. 业务子系统优先级

| 优先级 | 当前缺口／新能力 | 新规则与依赖 | 现有操作为什么无法组合得到 | 程序化验证与覆盖目标 |
| --- | --- | --- | --- | --- |
| P1，成本中等 | Membership 邀请、加入、停用/移除的生命周期 | 加入→active_count 上升→席位不足；扩席→可加入；移除→可降席→降套餐；Owner 不可删除、跨组织邀请隔离、待处理状态 | 当前唯一成员写操作只改 role，不改变 status 或成员数，因此 active_count 在所有合法写序列中不变 | 独立 Reference transition、唯一成员/Owner 不变量、容量与 active_count 不变量、许可矩阵；反事实检查每条成员—席位—套餐边 |
| P2，成本中至高 | Subscription 激活、续期与 Invoice 支付的关联生命周期 | 支付→激活/续期→可变更套餐；支付失败/未支付分支；幂等激活；账单与订阅周期明确关联 | 当前 expired 不能转 active，unpaid 不能变 paid；Invoice 没有 subscription/cycle 关联，冻结 clock 不能由工具偷偷推进 | 原子支付/激活规则、确定性 payment fixture、周期边界、双重支付/激活防护、跨组织关联与终态验证；补足前态迁移而非只在初始世界随机抽状态 |
| P3，成本较高 | Billing 余额/贷项与退款资金链 | 支付与退款影响可用余额；多个账单共享额度；退款总额/余额守恒；原支付渠道与重复/部分退款规则 | 当前每张账单独立、只能全额退款，无余额/共享额度实体；无法用重复 refund 模拟资金依赖 | 独立账本 Reference、金额守恒/幂等键、单账单与账户累计上限、相关资源隔离；补足跨账单与订阅—财务的真实因果链 |

P1 能直接连接当前已有的席位/套餐规则，研究收益与成本最优。P2 再连接当前
彼此独立的订阅和账单，必须先明确原子性与失败语义。P3 的守恒规则更有研究
价值，但建模与验证成本较大，应在前两者的标准任务集稳定后加入。

每项扩展先写可独立于 Engine 的 Reference 与状态不变量，再增加状态迁移和
目标生成。新增业务必须提升可验证依赖或决策分支覆盖；不应为了扩充数量
降低授权、放宽退款窗口或改变现有 Oracle 判错标准。

## 4. 下一阶段的验收门槛

- 版本化标准任务 Manifest 与两个评测轨道的明确边界。
- Train/Test 结构重叠按策略达到可解释目标，所有留出规则组合在 Test 任务中
  实际用到，且所需原子能力在 Train 可见。
- 依赖链有真实 Reference 反事实证据；信息依赖、因果深度未识别时明确 Unknown。
- 每项新增生命周期都有合法/拒绝/临界/重复执行和事件回放验证；保留参考与
  Sandbox 语义的区别，不把失败的恶意尝试算作成功违规。
- 分别给出任务完成、Oracle 违规、结构/分支覆盖、预算与多次运行方差；公开
  审计程序与足够的可复现证据，私有 Test 实例继续由评测方管理。
