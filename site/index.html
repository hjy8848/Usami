完成一道题之后，下一步该学什么？

设想一个能办理机票改签的智能客服。顾客先要求“越早到越好”，看过方案后又改口：“下午到就行，费用别超过 300 元。”客服需要重新比较航班、座位、费用和当前确认，才能执行改签。

它可能沿用旧方案而出错，也可能反复核对后终于办对。两种经历都有信息：错误暴露已经失守的边界；成功过程中的补救、遗漏和计划修正，则留下值得继续考察的线索。

要把这些经历变成持续学习，我们需要两样东西：能容纳新任务、又能客观判断结果的业务世界；能从当前表现中找到下一道有价值挑战的出题者。

Usami 解决前一个问题，VAST-CoEvo 研究后一个问题，并让出题者与服务者共同积累经验。

01 Usami Benchmark

任务，从世界里的关系组合出来

Usami 把业务对象、状态、权限和操作规则放进一个可以实际运行的世界。企业里有员工、订阅和账单，云项目里有服务器、配额与依赖，酒店里有日期库存、预订与具体房间。一次操作会改变状态，也会改变后续操作的条件。

因此，复杂性来自业务关系本身。付款成功之后，项目仍需恢复；组织负责人也可能没有项目操作权限；应用启动之前，依赖与配额必须同时满足。下面这张图展示 CloudOps 中这些条件如何连接。

八类业务世界，各有自己的约束

世界库覆盖不同业务语义。它们共享交互与证据的组织方式，同时各自保留原生状态、规则和操作。

SaaS · 企业软件成员权限、订阅席位、账单与退款 CloudOps · 云资源项目角色、依赖、配额与资源生命周期 FulfillmentOps · 履约库存守恒、订单分配与运输状态 StayOps · 酒店跨日期库存、预订与物理房间分配 AfterSales · 售后退换条件、凭证、报价、收货与结算 Airline · 航空联程、舱位、票规、费用与重新确认 Property · 物业故障分级、维修方案、预约与住户确认 Education · 教育课程资格、师生排期、学习进度与费用

为什么一个世界能产生许多任务？

任务由几类选择共同决定：用哪个已有身份，处理哪些对象，组合什么业务目标，允许哪些操作。对象之间的关系又会形成先后条件；相同目标可以有不同的合法完成路径。

在同一个云世界中，可以请求启动数据库、让数据库与应用一起上线、扩容后部署完整服务，或同时启动两个项目的资源。任务构造接口在支持的操作与目标范围内检查这些组合。世界初态与规则始终固定，新的任务来自既有关系。

身份已有用户与权限

谁在什么项目中，能做什么？

对象与关系单实体或跨实体

资源依赖、账单、库存和时间怎样连接？

目标组合业务结果

启动、恢复、调整、安排，哪些结果要一起达成？

执行路径多种合法解法

由状态与规则约束顺序，按实际结果判断。

在同一个世界里，亲手组合一次

下面只取云业务的一个小切片。选一位已有成员、一个项目和希望运行的资源。先尝试完整部署，再只请求启动 app，或更换成员：你会看到同一组对象为什么能形成不同任务。

目标相同，也可以有不同路径

alpha 中的 db 与 cache 互相独立：先启动哪一个都可以，app 在两项上游运行后启动即可。换到链式依赖项目，就必须遵守链的顺序。评价检查业务目标、状态变化与安全约束，而不要求照抄某条参考步骤。

题目成立，与 Service 答对，是两次判断

让只有 Viewer 权限的用户请求启动服务器，可以是一道有效的拒绝题。规则先确定它应当被拒绝；如果 Service 正确拒绝，它就答对了；如果实际成功执行了违规写入，才形成业务错误证据。

Reference 给出规则预期，Engine 记录真实执行，Oracle 核对行为与状态变化。Replay 让整段记录可以再次检查。这样，任务发现者负责提出挑战，业务规则负责判定答案。

这套世界与验证接口可以独立用于标准任务评测、规划方法、任务生成和开放探索。VAST-CoEvo 是使用 Usami 的一种方法，Benchmark 本身并不依赖进化流程。

02 VAST-CoEvo

从已经发生的交互，找到下一道挑战

先让 Service 完成初始任务，留下顾客对话、查询、动作、计划修正和实际结果。Designer 读取这些经过核验的经历，提出关于 Service 薄弱环节的假设，再从冻结世界中选择能检验假设的新任务。

失败轨迹用于追查、复现和扩展已经暴露的问题。成功轨迹则用来检查：那些依靠补查或修正才完成的判断，在相邻业务条件下是否仍然可靠。后续挑战有明确的经历来源。

三个角色，各自做好一件事

Designer 负责发现任务，Customer 把任务变成自然对话，Service 处理业务。固定 Customer 的角色策略，能够让挑战选择的变化与顾客交互行为的变化分开；固定策略仍会依据 Service 的真实回复多轮沟通。

Designer / 选题

下一题，考哪里？

分析成功与失败的轨迹，选择已有世界、身份、对象和目标，构成针对性的挑战。

Customer / 对话

把需求说成真实交互

提出请求、回答追问、补充信息和确认方案。角色策略固定，具体对话随真实回复展开。

Service / 业务

查清事实，再做决定

自主查询、规划和调用业务工具。完成合法请求，准确拒绝规则禁止的操作。

为什么让出题者也学习？

Service 的薄弱点会随着经验变化。修复依赖检查之后，反复考同一道依赖题能带来的新信息就减少了。Designer 需要积累的是寻找下一处边界的方法，而不只是记住哪些资源曾经出过错。

Service 学习如何处理新挑战；Designer 根据更新后的 Service 表现修订选题方法。双方的变化共同改变下一轮学习机会的来源。

用 Skill 保存两种不同的经验

同一段依赖轨迹，进入两份不同的“工作手册”。Service 保存业务判断原则，Designer 保存寻找和验证薄弱环节的方法。下一轮模型调用使用各自当前版本的 Skill，基础模型权重保持固定。

Designer Skill / 怎样考察

当 Service 补查后才完善依赖计划，选择有多层上游的既有任务，检查它能否在首次写入前识别完整前置条件。

Service Skill / 怎样处理

启动前核实完整依赖与当前状态；需要额外操作才能完成目标时，先确认操作范围和顾客授权。

Skill 让经验成为可读、可检查、可继承的策略。每代分别记录两份经验及其来源，下一代在新的交互中继续使用和修订，形成递归过程。

03 相关研究

两个不同的研究对象，一条相互连接的学习链

Usami 与 VAST-CoEvo 回应两个相连的问题：业务任务怎样从真实规则关系中组合出来；交互经验又怎样改变下一代的出题策略与执行策略。

01 / 交互式 Benchmark

τ-bench ↗

以多轮用户对话、领域工具和业务规则评测 Agent，并核对最终数据库状态。

Usami 的任务单位

从冻结业务实例中的既有身份、关系与目标组合任务；Service Task 与开放式 Discovery 分为独立 Track。

02 / 自主任务生成与学习

Self-Challenging Language Model Agents ↗

Challenger 探索工具环境，生成 Code-as-Task。论文实验固定 Challenger，用生成任务训练 Executor。

VAST-CoEvo 的递归对象

Designer 的选题方法也跨代更新，与 Service 的业务 Skill 分开积累；真实交互证据连接两种策略。

03 / 递归自我改进

MASS ↗

搜索多 Agent 工作流，再将团队经验蒸馏进共享模型，由同一模型承担执行、优化与评价。

VAST-CoEvo 的学习载体

基础模型权重固定，Designer 与 Service 各自更新可审计的 Skill，在可执行业务世界中递归学习。

三条脉络分别锚定交互式评测、自主任务生成和递归学习。Usami 将可组合的业务基准作为环境，VAST-CoEvo 则把“下一题怎么选”和“业务怎么做好”设为两个不同的学习对象。

04 评价设计

发现能力和解决能力，分别衡量

Designer 找到更多问题与 Service 变得更可靠，是两个不同结果。评价同时跟踪两条变化，并在独立业务世界中比较保存的版本。

Designer

能否持续找到有价值的新挑战？

任务是否有效，是否发现可复现的新错误或业务边界，是否避免反复触发同一个问题。

Service

能否处理旧问题与新情境？

既要减少违规和错误拒绝，也要继续完成合法业务；在没有参与学习的世界中检查迁移。

共同过程

新挑战是否带来了新的学习？

比较固定与进化 Designer，以及不同代的 Service；同时记录覆盖、调用和 Token 成本。

配对比较固定世界初态、身份、模型、工具和预算。训练保存证据与版本；训练后的对照只读取这些版本。独立 Held-out 的结果不回流训练。

实现与研究接口

业务世界、任务与执行记录均有明确版本。原始对话、工具调用、状态事件、Oracle 判断、Skill 更新及成本保留为可回放证据。

Benchmark Track 与训练协议

Service Task 固定业务目标，测量执行能力；Customer Discovery 固定世界、身份、目标 Service 与预算，由 Customer 自主提出逐轮请求。VAST-CoEvo 的 Frozen Task Discovery 另设 Designer 选题层，保持 Customer 对话策略固定。

当前训练默认按静态约束发布有效 SkillPatch。Schema、角色范围、父版本及安全检查保留，NOOP 或失败沿用父版本。动态性能评价与独立对照使用单独的评价入口。

  • 项目代码业务环境、Agent 接口与进化实现
  • Benchmark 协议与领域固定任务、开放探索与版本化实例
  • Frozen-World Task Discovery任务组合、证据流与递归训练
  • Skill 更新协议静态检查、版本继承与独立评价
